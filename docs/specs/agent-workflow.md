# Работа агента

## Подготовка и согласование

1. Определи цель, сценарии и затронутые платформы. Если интерфейс меняется, прочитай правила `Heartbeat-design`, сделай прототип в Pencil, сохрани `.pen` в [общем клоне дизайна](../setup.md#design) и пройди сценарии с оператором. Для остальных задач зафиксируй результат оценки UI/UX.
2. Составь план с требованиями и критериями приёмки. Укажи границы модулей, затронутые модули, интерфейсы и потоки данных. Опиши обработку ошибок там, где она влияет на поведение.
3. Покажи оператору план и результаты апробации. Получи явное согласование до реализации.

## Реализация

1. Создай ветку от актуальной `master`. Сделай один пустой стартовый коммит и открой draft PR с согласованным планом.
2. Выполняй план логическими шагами. Оформляй самостоятельные изменения отдельными коммитами. После каждого проверенного коммита отправь ветку и обнови PR. Укажи SHA, результат проверки и оставшуюся работу.
3. После итоговых проверок переведи PR в Ready for review.

## Ревью владельцем

Агент заполняет последний раздел описания PR `REVIEW CHECKLIST` по мере появления коммитов с изменениями. Для каждого коммита агент добавляет одну галочку. В строке галочки он указывает ссылку с коротким SHA и краткое название. Под галочкой он добавляет вложенный список без галочек — проверяемые результаты.

```markdown
- [ ] **[1234567](https://github.com/aequicor/Heartbeat-v2/commit/1234567890abcdef1234567890abcdef12345678)** — Проверки запуска
  - В журнале есть `Heartbeat started`.
  - Desktop-процесс завершается с кодом `0`.
```

Владелец проверяет весь diff текущего HEAD и отмечает галочку каждого коммита. Затем он оставляет новый комментарий из одной строки `/reviewed <SHA или ссылка>`. Подходит полный SHA или сокращение от 7 символов, которое GitHub разрешает в текущий HEAD. Прямая или Markdown-ссылка должна вести на текущий коммит этого PR. Вариант команды `/revied` также принимается. Комментарий должен содержать одну строку: команда начинается ровно с `/reviewed` или `/revied` и отделяется пробелом, поэтому `/reviewed-anything` и многострочный текст не принимаются — workflow завершается с ошибкой разбора команды. Указанный SHA workflow сверяет с текущим HEAD и передаёт зафиксированный SHA всем проверкам: если аргумент не является префиксом HEAD, проверки не запускаются.

Workflow проверяет, что владелец отметил все галочки до отправки комментария, чек-лист относится к текущему HEAD, а галочки коммитов и списки проверок совпадают в событии и текущем описании. Workflow также принимает существующие плоские чек-листы. Если в PR остаются незакрытые обсуждения, workflow перечисляет их и число в ответе, но не отменяет подтверждение: статус `owner-review` выставляется, а слияние GitHub выполняет после закрытия обсуждений. Затем GitHub App выставляет `owner-review` и запрашивает squash-слияние для проверенного SHA. GitHub ждёт успешного CI, закрытия обсуждений и выполнения остальных требований ветки. После слияния GitHub удаляет ветку PR. При новом коммите агент обновляет SHA чек-листа и сохраняет отметки владельца, а новая галочка остаётся пустой. После перезаписи истории — force push, rebase, amend или squash — агент обновляет галочки перезаписанных коммитов и сбрасывает отметки только в них: прежние подтверждения относятся к исчезнувшим коммитам. Галочки остальных коммитов сохраняют отметки. Владелец отмечает сброшенные и новые галочки и подтверждает новый HEAD.

GitHub Actions публикует в PR ответ со ссылкой на команду и журнал. При отказе ответ сообщает причину и подсказывает, что исправить.

## Требования и проверка

| ID | Требование | Источник | Критерий проверки |
| --- | --- | --- | --- |
| HB-WORK-001 | Если задача меняет интерфейс, агент должен подготовить прототип и пройти затронутые сценарии с оператором до реализации. | Цикл прототипирования из постановки проекта | Проверить путь к макету и запись согласования в плане. |
| HB-WORK-002 | Когда оператор согласует план, агент должен открыть draft PR с пустым diff до первого коммита с реализацией. | Порядок PR из постановки проекта | Сверить время согласования, историю ветки и начальное состояние PR. |
| HB-WORK-003 | Когда агент завершает логический шаг, он должен проверить шаг, отправить его коммит и обновить описание PR. | Порядок реализации из постановки проекта | Сверить историю ветки со статусом и результатами проверок в PR. |
| HB-WORK-004 | Пока владелец не отметил все галочки в описании PR и не оставил комментарий `/reviewed` для текущего HEAD, GitHub должен блокировать слияние PR в `master`. | Защита ветки из постановки проекта | Проверить блокировку без комментария и с неполным чек-листом, доступность после подтверждения владельцем и повторную блокировку после нового коммита. |
| HB-WORK-005 | Когда агент добавляет коммит с изменениями, он должен добавить в чек-лист PR одну галочку для этого коммита. В строке галочки должна быть одна ссылка на коммит, под галочкой — вложенный список, по одному проверяемому результату на пункт. | Согласованный формат чек-листа | Сверить коммиты с галочками и проверить, что каждый пункт списка описывает один результат. |
| HB-WORK-006 | Когда владелец отправляет команду `/reviewed` для чек-листа с галочками коммитов, workflow должен отклонить повторный коммит, галочку без списка проверок, ссылку с неверным SHA или изменение строки галочки после комментария. | Согласованный формат чек-листа и проверка текущего HEAD | Прогнать тесты валидатора для полного чек-листа и каждого отказа. |
| HB-WORK-007 | Когда владелец отправляет подтверждение ревью, а в PR остаются незакрытые обсуждения, workflow должен сообщить в ответе их число и ссылки, не отменяя публикацию статуса `owner-review`. | Запрос владельца от 5 ноября 2026 | Отправить подтверждение в PR с незакрытыми обсуждениями и сверить статус с текстом ответа workflow. |
| HB-WORK-008 | Когда агент добавляет коммит к ветке PR, он должен сохранить отметки владельца в чек-листе и обновить маркер на новый HEAD. Когда история ветки перезаписана, он должен сбросить отметки только в галочках перезаписанных коммитов. | Запрос владельца от 5 ноября 2026 | Сверить описание PR после обычного коммита, после force push и после перезаписи одного коммита: отметки сохранены, сброшены и сброшены частично. |
