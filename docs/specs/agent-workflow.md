# Работа агента

## Подготовка и согласование

1. Определи цель, сценарии и затронутые платформы. Если интерфейс меняется, сделай прототип в Pencil, сохрани `.pen` в `design/` и пройди сценарии с оператором. Для остальных задач зафиксируй результат оценки UI/UX.
2. Составь план с требованиями и критериями приёмки. Укажи границы модулей, затронутые модули, интерфейсы и потоки данных. Опиши обработку ошибок там, где она влияет на поведение.
3. Покажи оператору план и результаты апробации. Получи явное согласование до реализации.

## Реализация

1. Создай ветку от актуальной `master`. Сделай один пустой стартовый коммит и открой draft PR с согласованным планом.
2. Выполняй план логическими шагами. Оформляй самостоятельные изменения отдельными коммитами. После каждого проверенного коммита отправь ветку и обнови PR. Укажи SHA, результат проверки и оставшуюся работу.
3. После итоговых проверок переведи PR в Ready for review.

## Ревью владельцем

Агент заполняет последний раздел описания PR `REVIEW CHECKLIST` по мере появления коммитов с изменениями. Для каждого коммита агент добавляет одну группу. В заголовке группы он указывает ссылку с коротким SHA и краткое название. Под заголовком он добавляет по одной галочке на проверяемый результат.

```markdown
**[1234567](https://github.com/aequicor/Heartbeat-v2/commit/1234567890abcdef1234567890abcdef12345678)** — Проверки запуска

- [ ] В журнале есть `Heartbeat started`.
- [ ] Desktop-процесс завершается с кодом `0`.
```

Владелец проверяет весь diff текущего HEAD и отмечает все пункты. Затем он оставляет новый комментарий из одной строки `/reviewed <SHA или ссылка>`. Подходит полный SHA или сокращение от 7 символов, которое GitHub разрешает в текущий HEAD. Прямая или Markdown-ссылка должна вести на текущий коммит этого PR. Вариант команды `/revied` также принимается.

Workflow проверяет, что владелец отметил все пункты до отправки комментария, чек-лист относится к текущему HEAD, а заголовки групп и пункты совпадают в событии и текущем описании. Workflow также принимает существующие плоские чек-листы. Если в PR остаются незакрытые обсуждения, workflow перечисляет их и число в ответе, но не отменяет подтверждение: статус `owner-review` выставляется, а слияние GitHub выполняет после закрытия обсуждений. Затем GitHub App выставляет `owner-review` и запрашивает squash-слияние для проверенного SHA. GitHub ждёт успешного CI, закрытия обсуждений и выполнения остальных требований ветки. После слияния GitHub удаляет ветку PR. При новом коммите агент обновляет SHA чек-листа и сбрасывает отметки. Владелец повторяет проверку и подтверждение.

GitHub Actions публикует в PR ответ со ссылкой на команду и журнал. При отказе ответ сообщает причину и подсказывает, что исправить.

## Требования и проверка

| ID | Требование | Источник | Критерий проверки |
| --- | --- | --- | --- |
| HB-WORK-001 | Если задача меняет интерфейс, агент должен подготовить прототип и пройти затронутые сценарии с оператором до реализации. | Цикл прототипирования из постановки проекта | Проверить путь к макету и запись согласования в плане. |
| HB-WORK-002 | Когда оператор согласует план, агент должен открыть draft PR с пустым diff до первого коммита с реализацией. | Порядок PR из постановки проекта | Сверить время согласования, историю ветки и начальное состояние PR. |
| HB-WORK-003 | Когда агент завершает логический шаг, он должен проверить шаг, отправить его коммит и обновить описание PR. | Порядок реализации из постановки проекта | Сверить историю ветки со статусом и результатами проверок в PR. |
| HB-WORK-004 | Пока владелец не отметил все пункты в описании PR и не оставил комментарий `/reviewed` для текущего HEAD, GitHub должен блокировать слияние PR в `master`. | Защита ветки из постановки проекта | Проверить блокировку без комментария и с неполным чек-листом, доступность после подтверждения владельцем и повторную блокировку после нового коммита. |
| HB-WORK-005 | Когда агент добавляет коммит с изменениями, он должен добавить одну группу в чек-лист PR. В заголовке должна быть одна ссылка на коммит, под заголовком — по одному проверяемому результату на пункт. | Согласованный формат чек-листа | Сверить коммиты с заголовками групп и проверить, что каждый пункт описывает один результат. |
| HB-WORK-006 | Когда владелец отправляет команду `/reviewed` для чек-листа с группами, workflow должен отклонить повторный коммит, группу без пунктов, ссылку с неверным SHA или изменение заголовка после комментария. | Согласованный формат чек-листа и проверка текущего HEAD | Прогнать тесты валидатора для полного чек-листа и каждого отказа. |
| HB-WORK-007 | Когда владелец отправляет подтверждение ревью, а в PR остаются незакрытые обсуждения, workflow должен сообщить в ответе их число и ссылки, не отменяя публикацию статуса `owner-review`. | Запрос владельца от 5 ноября 2026 | Отправить подтверждение в PR с незакрытыми обсуждениями и сверить статус с текстом ответа workflow. |
